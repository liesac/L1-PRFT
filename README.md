# Sport Activity File Reader

A locally deployed web application for parsing, analyzing, and visualizing sports activity data from `.fit` files. Built with a Python/FastAPI backend and a Vanilla JavaScript SPA frontend.

---

## Project Overview

The application accepts `.fit` activity files (produced by GPS sports devices), processes them entirely in-memory, and returns structured telemetry and statistics to the browser. There is no database, no authentication, and no network calls at runtime beyond the local loopback.

**Key features:**
- Upload and parse `.fit` activity files
- Unified multi-metric telemetry chart (Cadence, Elevation, Heart Rate, Power, Speed, Temperature)
- Interactive GPS route map
- Per-metric performance widgets (average, maximum, minimum)
- Automated activity insights

---

## Architecture

The application is deployed as a single unit:

```
Browser
  └── GET /         → FastAPI serves compiled SPA (StaticFiles)
  └── POST /api/v1/ → FastAPI route handlers
```

The FastAPI backend acts as both the REST API provider and the static file server for the compiled frontend. API routes are scoped under `/api/v1/` to avoid collisions with static assets. This eliminates CORS overhead in production.

The backend follows **Clean Architecture** with four layers:

| Layer | Responsibility |
|---|---|
| `domain/` | Business entities, value objects, pure domain services |
| `application/` | Use cases orchestrating domain operations |
| `infrastructure/` | FIT file parsing via `fitdecode` |
| `presentation/` | FastAPI routes, Pydantic schemas, dependency injection |

The frontend is organized by feature:

| Module | Responsibility |
|---|---|
| `core/api/` | HTTP client and response normalization |
| `core/state/` | Centralized state store with subscriptions |
| `core/events/` | Pub/sub event bus for cross-feature signaling |
| `features/upload/` | File selection, validation, and submission |
| `features/charts/` | Chart.js telemetry visualization |
| `features/maps/` | Leaflet GPS route rendering |
| `features/summary/` | Performance stat widgets |
| `features/status/` | Loading and error state banners |

## Local Development Setup

### Prerequisites

- Python 3.12+
- Node.js 20+
- npm 10+

### Backend

```bash
cd backend

# Install dependencies (editable mode with dev extras)
python -m pip install -e .[dev]

# Start the development server
python -m uvicorn src.presentation.main:app --reload --host 127.0.0.1 --port 8000
```

### Frontend

```bash
cd frontend

# Install dependencies
npm install

# Start the Vite dev server
npm run dev
```

Open the Vite dev URL (default: `http://localhost:5173`). The Vite proxy forwards all `/api/*` requests to the FastAPI server at `http://127.0.0.1:8000`.

## Build & Deployment

To produce a deployable build (frontend compiled into `backend/static/`):

```bash
cd frontend
npm run build
```

Then run the backend alone — it serves both the API and the compiled SPA:

```bash
cd backend
python -m uvicorn src.presentation.main:app --host 127.0.0.1 --port 8000
```

Open `http://127.0.0.1:8000`.

## Design Decisions

- **No persistence** — Every request is fully stateless. No database, no session, no disk writes.
- **Single deployment unit** — FastAPI serves both the API and the SPA, eliminating CORS in production.
- **Clean Architecture** — Domain logic is framework-agnostic and independently testable.
- **Pure functions preferred** — Domain services and frontend utilities avoid shared mutable state.
- **No new runtime dependencies without approval** — The dependency list is intentionally minimal and locked.
- **Test-first** — Tests are written before implementation for each task.
